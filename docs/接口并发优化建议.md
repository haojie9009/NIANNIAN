# 接口并发优化建议

> 仅分析和建议，不修改任何代码。

---

## 一、当前并发架构全景

| 层级 | 现状 | 说明 |
|------|------|------|
| Web 框架 | FastAPI + Uvicorn | ASGI 单进程单线程事件循环 |
| 启动方式 | `uvicorn.run(reload=True)` | `main.py:298`，开发模式 |
| LLM 调用 | `openai.OpenAI`（同步 requests） | `llm_client.py` 全部函数 |
| 视频/图片生成 | `requests.post()` + `time.sleep()` 轮询 | `llm_client.py` 图片/视频/BGM |
| SSE 流 | 同步 generator + `StreamingResponse` | `routers/agent.py:176` |
| WebSocket | `asyncio` 原生异步 | `routers/agent_realtime.py` |
| 文件 I/O | 同步 `Path.write_*` / `open()` | `core/storage.py` |
| OSS 推送 | 每次 `threading.Thread` 新线程 | `core/oss_sync.py:101` |
| 后台任务 | `BackgroundTasks` + daemon thread | `routers/pipeline.py:26` |
| 限流/队列 | **无** | 没有任何限流机制 |

## 二、CRITICAL — 阻塞事件循环的并发杀手

### 1. SSE 端点在事件循环上执行阻塞调用

**位置**: `routers/agent.py:143-208`

```python
@router.post("/chat")
async def agent_chat(...):  # ← async def → 直接在事件循环线程上运行
    def generate():         # ← 同步 generator
        stream = client.chat.completions.create(...)  # ← 阻塞 requests 调用
        for chunk in stream:
            yield ...
    return StreamingResponse(generate(), ...)
```

**问题**: `async def` 让 FastAPI 直接在事件循环线程上执行此函数。`generate()` 中的 `client.chat.completions.create(stream=True)` 是一个阻塞的 HTTP 调用，持续 10-30 秒，期间**整个事件循环被冻结**——所有其他请求（包括健康检查、静态文件、WebSocket 等）全部排队等待。

**同样问题**: `agent_asr()` 中的 `client.audio.transcriptions.create()` 也是同步阻塞调用。

**影响**: 在 1 个用户正在流式对话时，其他用户的所有请求都被阻塞。

### 2. Pipeline 同步端点串行阻塞线程池

**位置**: `routers/pipeline.py:13-28`

```python
@router.post("/run/{step}/{sid}")
def run_step(step, sid, background_tasks):
    return sm.run_pipeline_step(sid, step)  # ← 同步 def，进入 FastAPI 线程池
```

FastAPI 对 `def` 端点使用线程池执行（默认 ~40 个工作线程）。但每个 LLM 调用阻塞 10-60 秒，意味着：
- 40 个并发请求即可**耗尽整个线程池**
- 第 41 个请求开始排队，等待任意一个 LLM 调用完成
- `run_all`（`pipeline.py:91-97`）串行调用 MV01→MV02→MV03，单请求占用线程 90+ 秒

**影响**: 中等并发（10-40 用户同时操作）即可导致请求排队超时。

## 三、HIGH — 资源浪费与无界增长

### 3. OSS 推送无限制线程创建

**位置**: `core/oss_sync.py:82-101`

```python
def push_path(local_path):
    def _do():
        b = _get_bucket()
        b.put_object_from_file(key, str(local_path))
    threading.Thread(target=_do, daemon=True).start()  # ← 每次新建线程
```

**问题**:
- 每次文件写入都创建新线程，无上限、无池化、无队列
- 100 个并发写入 → 100 个线程同时创建
- Python 线程创建成本约 8KB 栈 + OS 开销，大量线程会拖慢调度器

**同样问题**: `delete_path()` 也是同样的模式（`oss_sync.py:132`）。

### 4. 视频/图片生成轮询阻塞

**位置**: `services/llm_client.py`

| 函数 | 阻塞时间 | 模式 |
|------|---------|------|
| `generate_video_kling()` | 最长 600s | `time.sleep(interval)` 轮询 |
| `generate_video_302ai_i2v()` | 最长 600s | `time.sleep(interval)` 轮询 |
| `generate_bgm_suno()` | 最长 300s | `time.sleep(15)` 轮询 |

每次调用占用一个线程（或事件循环）长达 10 分钟，期间线程完全被占用。

## 四、MEDIUM — 并发安全与数据一致性

### 5. `merge_dossier` TOCTOU 竞态

**位置**: `core/storage.py:231-255`

```python
def merge_dossier(user_id, memorial_id, patch):
    cur = get_dossier(user_id, memorial_id)  # ← 无锁读取
    merged = _merge(cur, patch)
    return save_dossier(user_id, memorial_id, merged)  # ← 有锁写入
```

两个并发请求同时合并 dossier 时：
- 请求 A 读到版本 V1
- 请求 B 读到版本 V1
- A 合并并写入 V2
- B 合并并写入 V2（**覆盖 A 的变更**）

**修复方向**: 将读取和写入放在同一个锁内，或使用文件级锁。

### 6. 后台线程写 session 的 stale data 风险

**位置**: `services/service_manager.py:1380-1488`

`_run_mv06_work()` 作为 daemon 线程运行，持有 session 字典的本地引用 `s`，在 LLM/TTS/BGM 等耗时操作期间，另一个请求可能已经修改了同一个 session。最终 `session_store.update(sid)` 用旧数据覆盖新数据。

### 7. storage 读操作无锁保护

**位置**: `core/storage.py`

| 函数 | 行号 | 状态 |
|------|------|------|
| `get_memorial()` | 140-141 | 无锁 |
| `get_dossier()` | 213-215 | 无锁 |
| `list_memorials()` | 126-138 | 无锁 |
| `list_assets()` | 286-287 | 无锁 |
| `read_conversations()` | 272-283 | 无锁 |

虽然 JSON 读操作在 CPython 中基本原子，但大文件读+反序列化期间如果有并发写入，可能读到不一致的中间状态。

## 五、LOW — 其他并发问题

### 8. `pipeline_runner.py` 全局状态无锁

**位置**: `services/pipeline_runner.py:26-29`

模块级 `mv_state` 字典无锁保护，如果此遗留模块仍在使用，两个并发请求会竞争修改状态。

### 9. OSS `_bucket` 初始化竞态

**位置**: `core/oss_sync.py:48-56`

`_LOCK` 已定义但从未使用。两个线程同时调用 `_get_bucket()` 时可能创建两个 Bucket 实例。实际上无害（幂等操作），但 `_LOCK` 的存在说明设计意图被遗漏了。

### 10. 无任何限流机制

整个代码库没有：
- 请求频率限制（per-IP / per-user）
- LLM API 调用速率控制
- 请求排队/退避机制
- 超时保护（除 HTTP 客户端自带外）

## 六、分阶段修复路线图

### Phase 1 — 紧急修复（1-2 天）

**优先级**: CRITICAL — 解决事件循环阻塞

| # | 修改 | 文件 | 效果 |
|---|------|------|------|
| 1.1 | `agent_chat` 从 `async def` 改为 `def` | `routers/agent.py:143` | 让 FastAPI 自动将 SSE 放入线程池，不再阻塞事件循环 |
| 1.2 | `agent_asr` 从 `async def` 改为 `def` | `routers/agent.py:212` | 同上 |
| 1.3 | 启动时配置线程池大小 | `main.py:298` | `uvicorn.run(workers=4)` 或多进程部署 |

**1.3 详细说明**:
```python
# 当前
uvicorn.run("main:app", host="0.0.0.0", port=8000, reload=True)

# 建议（生产环境）
uvicorn.run("main:app", host="0.0.0.0", port=8000, workers=4)
# 或使用 gunicorn + uvicorn workers:
# gunicorn main:app -w 4 -k uvicorn.workers.UvicornWorker
```

### Phase 2 — 异步化 LLM 调用（3-5 天）

| # | 修改 | 文件 | 效果 |
|---|------|------|------|
| 2.1 | 全局替换 `openai.OpenAI` → `openai.AsyncOpenAI` | `llm_client.py` | LLM 调用变为非阻塞 |
| 2.2 | SSE generator 改为 `async def generate()` + `await` | `routers/agent.py:176` | 真正的事件驱动流 |
| 2.3 | `time.sleep()` → `asyncio.sleep()` | `llm_client.py` 轮询函数 | 轮询期间不占用线程 |
| 2.4 | `requests` → `aiohttp` 或 `httpx.AsyncClient` | `llm_client.py` 图片/视频/BGM | HTTP 调用非阻塞 |

**2.1 示例改造**:
```python
# 当前（阻塞）
client = openai.OpenAI(api_key=..., base_url=...)
resp = client.chat.completions.create(model=..., messages=...)

# 改造后（非阻塞）
client = openai.AsyncOpenAI(api_key=..., base_url=...)
resp = await client.chat.completions.create(model=..., messages=...)
```

**2.2 SSE 改造**:
```python
# 当前（同步 generator）
def generate():
    stream = client.chat.completions.create(..., stream=True)
    for chunk in stream:
        yield f"data: {payload}\n\n"

# 改造后（异步 generator）
async def generate():
    stream = await client.chat.completions.create(..., stream=True)
    async for chunk in stream:
        yield f"data: {payload}\n\n"
```

### Phase 3 — 并发安全与资源管控（2-3 天）

| # | 修改 | 文件 | 效果 |
|---|------|------|------|
| 3.1 | `merge_dossier` 加锁包裹读+写 | `core/storage.py:231` | 消除 TOCTOU 竞态 |
| 3.2 | OSS 推送改用有界线程池 | `core/oss_sync.py:101` | 限制并发线程数（如 4 个） |
| 3.3 | 使用 `_LOCK` 保护 `_get_bucket` | `core/oss_sync.py:48-56` | 消除 bucket 初始化竞态 |
| 3.4 | 添加请求超时中间件 | `main.py` middleware | 防止慢请求无限挂起 |
| 3.5 | 添加简单限流（per-IP） | `main.py` middleware | 防止 API 滥用 |

**3.2 OSS 线程池改造**:
```python
# 当前：每次新线程
threading.Thread(target=_do, daemon=True).start()

# 建议：有界线程池
_OSS_POOL = concurrent.futures.ThreadPoolExecutor(max_workers=4, thread_name_prefix="oss")
_OSS_POOL.submit(_do)
```

**3.4 超时中间件**:
```python
@app.middleware("http")
async def timeout_middleware(request, call_next):
    try:
        return await asyncio.wait_for(call_next(request), timeout=120.0)
    except asyncio.TimeoutError:
        return JSONResponse({"error": "request timeout"}, status_code=504)
```

### Phase 4 — 架构级扩展（按需）

| # | 修改 | 效果 |
|---|------|------|
| 4.1 | 视频/图片生成迁移到 Celery/RQ 任务队列 | 长时间任务脱离请求线程 |
| 4.2 | 多 worker 部署（gunicorn + uvicorn workers） | 多进程并行，突破单进程限制 |
| 4.3 | Redis 作为分布式 session 存储 | 支持多实例水平扩展 |
| 4.4 | 引入 slowapi 做全局限流 | 精细化 API 速率控制 |
| 4.5 | 视频生成改为 webhook 回调模式 | 替代轮询，减少空等 |

**4.1 任务队列架构**:
```
用户请求 → API (立即返回 task_id)
              ↓
         Celery/RQ 队列
              ↓
      Worker 进程（独立于 API）
              ↓
    LLM 调用 / 视频生成 / BGM 生成
              ↓
    用户轮询 / WebSocket 推送结果
```
